واجهة Node دي موجودة داخل المستودع. النسخة المتاحة للتثبيت من npm تدعم QR. التوقيع للفاتورة المبسطة يعتمد على مزوّد توقيع يهيّئه التطبيق.

const invoicing = createInvoicing({
  environment: 'sandbox',

  issuance: {

const result = await invoicing.issueInvoice(invoiceJson, invoiceJson.id);
console.log(result.status);

csid فيه معرّف طلب الشهادة وbinarySecurityToken وsecret. store يحفظ سلسلة الفواتير ويمنع تكرار الإرسال. الفاتورة القياسية تستخدم التخليص. المبسطة تستدعي مزوّد التوقيع أولًا ثم تستخدم الإبلاغ.

  • XML فقط عبر generateXml(invoiceJson, chainLink).
  • إبلاغ XML موقّع جاهز عبر invoicing.reportXml({ xml, invoiceHash }). تهيئة هذا المسار تحتاج environment وcsid فقط.
  • QR المرحلة الأولى عبر generatePhase1Qr(fields).

اختار نوع الفاتورة

مبسطة. أنشئ XML، وقّعه وأضف QR المرحلة الثانية على جهاز الإصدار، ثم أرسله للإبلاغ.

01

إنشاء ملف UBL XML

ابدأ بملف XML جاهز من الـERP، أو ولّد مسودة من بيانات نظام البيع. في المشروع افتح الديمو وشغّل npm run demo، ثم اضغط «إنشاء المسودة» و«تنزيل XML». في تطبيق Node استخدم buildInvoiceXml(draft) من src/xml/index.ts. الدالة ترجع نص XML تحفظه كملف UTF-8.

مثال توليد الملف من خادم Node

داخل مثال TypeScript في مجلد scripts/ مرّر بيانات فاتورتك المجهزة كـInvoiceDraft.

import { writeFile } from 'node:fs/promises';
import { buildInvoiceXml, type InvoiceDraft } from '../src/xml/index.js';

export async function saveInvoiceDraft(draft: InvoiceDraft) {
  const xml = buildInvoiceXml(draft);
  await writeFile('invoice-draft.xml', xml, 'utf8');
  return xml;
}
معاينة الملف الكامل بتنسيق للقراءة 

      

      
داخل الملف، cbc:UUID معرّف المستند، وcbc:InvoiceTypeCode يحدد نوعه. cac:InvoiceLine يحتوي على البنود، وcac:TaxTotal وcac:LegalMonetaryTotal يحتويان على الضريبة والإجمالي. العينة تعرض 200 ريال قبل الضريبة و230 ريال شامل الضريبة.

      
العينة مسودة تعليمية غير موقّعة. للتوقيع والتحقق جرّب العينة الرسمية المناسبة من حزمة SDK أو XML مُعدّ بنفس هوية جهاز الاختبار. خذ ICV وPIH من سلسلة الجهاز عند بناء مستندات متتالية.

02
التوقيع والهاش

      

        
وقّع XML المبسّط على خادم جهاز الإصدار باستخدام المفتاح الخاص وشهادة CSID المطابقة من نفس بيئة الاختبار. في حزمة زاتكا الرسمية، اضبط شهادة الاختبار والمفتاح وفق تعليمات نسختك، ثم شغّل الأمر الموثّق لإنشاء الملف الموقّع مع QR. استخدم عينة مبسّطة مناسبة للـSDK باسم simplified-input.xml.

        
fatoora -sign -qr -invoice simplified-input.xml -signedinvoice simplified-signed.xml

        
الناتج simplified-signed.xml والهاش الذي يعرضه الـSDK. افحص المستند النهائي باستخدام مدقق SDK. احتفظ بالهاش بصيغة Base64. إذا احتجت لاستخراجه مرة أخرى، استخدم أمر الهاش على الملف النهائي.

        
fatoora -generateHash -invoice simplified-signed.xml

      

      

        
جهّز ملف UBL القياسي، وافحصه بالـSDK. احسب الهاش وأرسل الملف للتخليص. في المسار الموضّح هنا، زاتكا تضيف الختم والـQR عند التخليص وتعيد الملف المعتمد.

        
fatoora -generateHash -invoice standard-input.xml

      

      
المفتاح الخاص يبقى على الخادم أو في مخزن المفاتيح. مكتبتنا الحالية تولّد المسودة وتستقبل ملفًا جاهزًا للإرسال. إنشاء توقيع Phase 2 داخل المكتبة نفسها لسه غير متاح.

03
استخراج QR ورسمه

      
خد حمولة QR من simplified-signed.xml بعد التوقيع والتجهيز بالـSDK. دي الحمولة المضمّنة في الفاتورة نفسها.

      
في المسار القياسي نفّذ الإرسال أولًا. بعد التخليص، فكّ clearedInvoice من Base64 واحفظه كملف cleared-invoice.xml. خد حمولة QR من الملف المرجع.

      
لو محتاج صورة PNG للعرض، اقرأ قيمة QR من XML وارسم النص نفسه. المثال التالي يعمل في PowerShell من جذر المشروع بعد تثبيت اعتماداته.

      

      
      
الـSDK هو اللي يجهّز حمولة Phase 2. مكتبة qrcode هنا ترسم الحمولة الموجودة فقط. رمز الديمو المولّد محليًا للمرحلة الأولى.

      
دليل زاتكا للفوترة الإلكترونية §4.1.2 و§4.2.2

    


    

      
04
إرسال الطلب من خادمك

      
هيّئ جهاز اختبار في Sandbox للحصول على شهادة إصدار اختبار وsecret. يبدأ المسار بـCSR وOTP، ثم شهادة امتثال، وفحص عينات، وإصدار شهادة الاختبار. خزّن بيانات الاعتماد على الخادم واستخدم شهادة نفس الجهاز والبيئة.

      
POST /invoices/reporting/single

      
الطلب فيه ثلاثة حقول. uuid من cbc:UUID في XML، وinvoiceHash هو الهاش المرجعي من الـSDK، وinvoice هو كامل ملف XML بترميز Base64. العميل يجهّز الحقول الثلاثة ويدير ترويسات Basic Auth وAccept-Version V2. المثال يستخدم TypeScript بعميل المستودع الداخلي، حيث sandboxCsid يأتي من مخزن الخادم.

05
اقرأ الرد واحفظ الحالة

      
الرد يرجع مباشرةً من نفس طلب HTTP. في الرد الخام اقرأ حالة العملية وvalidationResults. عميل المشروع يحولها إلى result.status وresult.diagnostics وresult.metadata. استدعِ const result = await submitInvoice(invoiceHash, sandboxCsid) واقرأ الحقول دي. لو رمى العميل ZatcaApiError افحص code وmetadata وoutcomeUnknown.

      
مثال مختصر لرد JSON من زاتكا

      

      

        
عند reported خزّن نتيجة الإبلاغ واحتفظ بملف XML الموقّع الذي أرسلته. زاتكا لا تحتاج ترجع نسخة XML جديدة لمسار الإبلاغ.

      

      

        
عند cleared فكّ result.clearedInvoiceBase64 واحفظ XML المرجع. العميل يتحقق من تطابق UUID قبل إرجاع حالة التخليص.

        
if (result.status === 'cleared') {
  await writeFile(
    'cleared-invoice.xml',
    Buffer.from(result.clearedInvoiceBase64, 'base64'),
  );
}
